How it works

Agents call home. The repository key stays on the server.

Backup machines never open a port, and they never keep a copy of the key that unlocks your repositories. They borrow a signature from the server for the length of a job.

assimilate-agent

Backup machine

Runs borg. Keeps one outbound WebSocket to the server. No inbound ports, no stored repository key.

WebSocket
+ signing relay
assimilate-server

Control plane

Holds the SSH key in its ssh-agent, schedules every job, indexes archives, serves the dashboard and API.

borg over SSH
(agent → repo)
borg serve

Repository host

Any SSH host with borg: a NAS, a VPS, a storage box. Its host key is pinned on first contact.

  1. The server starts a jobover the agent's existing WebSocket.
  2. The agent runs borgand connects to the repository host over SSH.
  3. The host asks for proofand the agent relays the signing request to the server.
  4. The server signsand archive data flows straight from agent to repository.
Features

Built for fleets, homelabs and the laptop that is never on at 2 a.m.

Everything you would otherwise glue together from cron, shell scripts and a notes file.

Scheduling

One schedule, every host, every copy

Name the hosts, the paths, the repositories and the timing once. Mark the offsite copy as best effort and an unreachable storage box becomes a warning, not a failed night.

  • Many hosts and repositories in one schedule, with paths and excludes per host
  • Catch-up runs for machines that were offline at the scheduled time
  • Retention, compact and integrity checks on their own schedules
  • Pre- and post-backup hooks with timeouts and captured output
  • Auto-disable after a set number of missed backups, so nothing fails quietly

Power management

Back up the NAS that sleeps most of the day

Before a run, Assimilate wakes the backup machine and the repository host, waits until both answer, runs borg and powers them down again. Every step lands in the run's timeline.

  • Wake-on-LAN for backup machines, repository hosts and the hosts a backup depends on
  • Start the agent over SSH when the machine is up but the service is not
  • Shut down or stop the agent once the backup is done
  • Per-schedule overrides for the one job that needs to behave differently

Dependency hosts

Backups that need another machine

Many backups depend on a third machine: the NAS whose share a pre-backup command mounts, the database server, the file server in the basement. Assimilate checks it before the run, wakes it if it sleeps, and waits for it. If it stays away, the run is skipped with the reason and caught up once it answers, instead of backing up an empty mount point.

  • Port checks for SMB, NFS, SSH or any port, from the server, before anything runs on the agent
  • Wake-on-LAN with its own settings, or shared with the repository host on the same box
  • Skip and catch up for machines that are not always online, or fail loudly for those that should be
  • Per schedule or per agent, so each machine lists exactly the shares it mounts

Virtual machines

libvirt domains, backed up incrementally

The agent finds the domains on its host and backs each one up as an incremental snapshot chain. A restore writes the disks back and defines the domain again.

  • Automatic discovery of every domain on the host
  • Incremental chains with a staging limit per domain
  • Restore and rebuild a domain from any archive

Access

Roles that match how your team works

Start with admin, operator and viewer. Add custom roles and groups as the team grows, grant permissions per repository, and keep a record of every change.

  • Per-repository permissions: view, back up, edit schedules, extract, delete
  • TOTP two-factor login with single-use recovery codes
  • Lockout on repeated failures, per address and per account
  • Audit log of every change, with filters and export
  • AES-256-GCM at rest for passphrases, TOTP secrets and notification credentials

Monitoring

Problems first, details on demand

The dashboard opens on what needs fixing: overdue schedules, failing targets, unprotected hosts and repositories near their quota. Everything updates live.

  • Needs-attention findings, protection coverage and upcoming work
  • Live logs while a backup runs, a full timeline afterwards
  • Alerts by email, webhook (Slack, Discord, ntfy, Gotify) or browser push
  • Quotas that warn, block new backups or disable a schedule

Restore

Find the file. Get it back.

Every archive is indexed on the server the moment it lands, so you can browse and search without touching the repository. Pick the point in time, find the file, then download it or put it back on the host.

Search every archive

Look for a file by name in one archive or across all of them, then jump straight to the right point in time.

Compare two points in time

Diff any two archives to see what was added, changed or removed before you restore.

Download or restore

Stream files or whole folders to your browser as tar.lz4, or restore them on the host, queued until its agent is back.

Phone and tablet

Your backups in your pocket, no app store needed

The web UI is a progressive web app. It adapts to phones and tablets, installs to your home screen in one tap, and opens full screen like a native app. Nothing to download, nothing to pay for, and it talks only to your own server.

  • Install from the browser on Android, iPhone and iPad with "Add to Home Screen"
  • Push notifications for failed backups, even when the app is closed
  • Run, cancel and check backups from the couch or the server room
  • Same login, same roles as on the desktop, with two-factor authentication

Who it is for

Three kinds of fleet, one tool

Homelabs

A NAS that sleeps, a hypervisor full of VMs, and a storage box offsite. Assimilate wakes what it needs, backs up the domains and shuts everything down again.

Laptops and desktops

Machines that are rarely on at the scheduled time. Catch-up runs start when they come back, and a missed-backup threshold tells you before a gap gets long.

Small teams

Servers several people look after. Roles, groups, per-repository permissions and an audit log keep access clear, and the API covers the rest.

Also included

The parts you would otherwise script yourself

Quotas with teeth

Warning and critical thresholds per repository and per repository host that notify, block new backups or disable a schedule before the disk fills.

Reverse SSH tunnels

For the host that cannot reach the server, the server opens a tunnel to it and reconnects on its own when the link drops.

Automate everything

Anything the UI does is available through the REST API, described by an OpenAPI specification and authorised with API tokens.

Get started

Running in a few minutes

One container for the server, one for PostgreSQL. Then:

  1. Open http://localhost:8080 and sign in as admin / admin. The first login asks for a new password.
  2. Add a repository on any SSH host that runs borg serve, or import one you already have.
  3. Add an agent and deploy it from the UI, or run the ghcr.io/alexmohr/assimilate-agent image.
  4. Create a schedule and follow the first run on the dashboard.
Full setup guide Configuration 
# docker-compose.yml
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_DB: borg
      POSTGRES_USER: borg
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:-borg_secret}
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U borg -d borg"]
      interval: 5s
      timeout: 3s
      retries: 5

  server:
    image: ghcr.io/alexmohr/assimilate:latest
    ports:
      - "8080:8080"
    environment:
      DATABASE_URL: postgres://borg:${POSTGRES_PASSWORD:-borg_secret}@db:5432/borg
      ASSIMILATE_SECRET_KEY: ${ASSIMILATE_SECRET_KEY:?must be set}
    volumes:
      - ssh_keys:/app/ssh
    depends_on:
      db:
        condition: service_healthy

volumes:
  pgdata:
  ssh_keys:

# then
export ASSIMILATE_SECRET_KEY=$(openssl rand -hex 32)
docker compose up -d
