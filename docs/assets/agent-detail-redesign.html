Assimilate · frontend proposal

Agent detail, unstacked

The Overview tab of an agent is where you land when a backup fails at 3am. Today it opens on a nine-row definition list, eight undifferentiated buttons and six configuration cards — and not one backup result. This is a redesign that puts the operational answer first and moves every setting behind one tab.

The problem

Everything is a card, so nothing is important

AgentDetailView.vue renders the Overview tab as one vertical run of .info-card blocks, each with the same border, the same .info-title and the same bottom-right Edit button. Two of them (Edit Identity, Deploy SSH Key) are not cards at all but inline expanders that shove everything below them down the page. The drawing below is to scale.

A wins on every line except tab-bar grammar, and that one is a taste argument against five concrete costs. Worth noting the two are not a one-way door: Settings is a self-contained component either way, so if the sub-nav ever outgrows the pane, promoting it to a route is a router change and nothing else.

Open question 2 · answered

Imported hosts keep every tab

No tab is dropped. An imported host has archives but no agent, so Schedules is empty — and an empty tab that explains itself is more useful than a tab bar whose contents shift depending on which host you opened. The position of Backups stays put across the fleet, and the tab is exactly where the emptiness ends the moment the host is adopted.

nas-archive was reconstructed from archives found in a repository, so there is no agent here to run a backup. Adopt the host to install one, or merge it into an agent that already exists.

The header carries a different meta strip — there is no version, revision or build timestamp for a host with no agent — and the two adoption actions take the primary slot. EmptyState already exists in the components directory; this is that component with copy that names the actual reason. Settings still opens: tags, hostname aliases and the danger zone all apply to an imported host.

Open question 3 · four options

What the success tile should actually count

The same tile, computed four ways, against three agents with different cadences. One finding first, because it eliminates half the field: GET /agents/:hostname/reports takes a limit and defaults to 50, and the view calls it with no parameters. Any window measured in days is therefore only honest while the agent runs fewer than fifty backups in that span. An hourly schedule does 720 a month.

The outage finally shows. One request, ?limit=30, inside the endpoint's default.

Last 30 runs 93%

Identical to option A, because for a daily agent 30 runs is 30 days.

Last 30 runs 97%
29 of 30 · past 7 months

Always has a sample, but the sample reaches back over half a year. The tile has to say so.

D. Last 30 runs, drawn count + outcome strip
Last 30 runs 5 failed Incident
past 30h · oldest left

Five contiguous reds read as one incident that has since recovered — which is the truth, and which no percentage can express.

Last 30 runs 2 failed
past 30d · oldest left

Two isolated reds, weeks apart: a flaky night, not a trend. Warnings get their own colour instead of being rounded into success.

Last 30 runs 1 failed
past 7 months · oldest left

The single red is the most recent run, which matters far more than 97% suggests. Position carries that; a percentage does not.

The recommendation is D

Headline the failure count, draw the outcomes, and name the real time span underneath. It is cadence-independent by construction, it fits ?limit=30 on an endpoint the view already calls, and it distinguishes one incident from a pattern — the distinction you actually open the page to make. When every run is clean the tile reads “All 30 clean” over a solid green strip.

Why not keep the percentage

A percentage is a fleet-level statistic that got put on a single-agent page. It answers “how does this host compare”, which is a Dashboard question, and it is worst exactly where it is needed most: the run that failed an hour ago moves it by one point on an hourly agent and twenty-five on a weekly one.

What this corrects

The earlier claim that every Overview number falls out of what the view already fetches was too strong. The tile as first drawn — a 30-day rate — is not derivable for a busy agent, because the reports call takes the server's default of 50. Option D needs no new endpoint, but it does need an explicit ?limit=.

Still open

Whether 30 is the right run count. Twenty fits the tile at a comfortable cell width and covers three weeks of daily backups; fifty is the endpoint's free ceiling but renders as hairlines. The strip should probably size itself to the tile and take whatever fits.

If we build it

What this costs

The proposal is deliberately backend-free: every number on the Overview tab is derivable from data the view already fetches on mount.

No new endpoints

Last backup, the outcome strip and the recent list all come from GET /agents/:hostname/reports, which the view already loads — though it will need an explicit ?limit=30, since the server defaults to 50 and the view sends nothing. Next run and the overdue badge come from /schedules and /stats/health, also already loaded. Repository count comes from /agents/:hostname/repos. “Run now” on a schedule row is the existing POST /schedules/:id/run.

Mostly existing components

BaseTabs, BaseModal, BaseSegmented, EntityStatusBadges, EntityTags, BackupProgressCard, EmptyState and AgentDangerZone all carry over. New: an AgentHeader, an AgentOverviewTab, an AgentBackupsTab and an AgentSettingsTab that hosts the existing panels.

Shrinks the view

AgentDetailView.vue is 1,320 lines carrying the tab shell, the backup list, two inline expanders, three dialogs and the WebSocket wiring. Splitting along the four tabs follows the same pattern F-24 applied to RepoDetailView, which came out at 367 lines.

Settled above

The three open questions are answered in their own sections: Settings is a fourth tab, imported hosts keep every tab, and the success tile counts the last 30 runs rather than a span of days. What is still open is the run count itself, and whether the strip should size to the tile.
